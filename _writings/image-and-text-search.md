‘흰색 운동화’를 찾는 사람에게 ‘화이트 스니커즈’도 보여주고 싶습니다. 상품명을 글자 그대로 비교하는 검색에서는 이 상품이 빠집니다. 이름을 모르고 사진만 가진 사람에게는 검색어를 입력하는 것부터 어려운 일이죠.

사진으로 비슷한 상품을 찾고, 이름이 달라도 뜻이 가까운 상품을 찾으려면 사진과 글을 비교할 방법이 필요합니다. 여기에 관련 상품을 먼저 보여주고 같은 사진이 결과를 채우지 않게 하는 규칙도 있어야 합니다. 이 기능들을 GPU 서버와 별도 벡터 DB, 검색 엔진을 상시 운영하지 않고 만들 수 있을까요?

저희 구성에서는 상품 사진과 이름을 미리 숫자 목록으로 바꿔 상품 테이블에 저장합니다. 검색할 때는 입력한 사진이나 검색어만 바꾸고, 저장된 목록과 비교해 후보를 찾습니다. 그다음 단어와 상품 종류, 중복 정도로 순서를 정합니다. 대량 등록에는 GPU를 빌려 쓰지만 사진 검색 한 건은 검색 서버의 CPU에서 처리합니다.

오른쪽에서는 기존 검색 서버와 PostgreSQL이 검색을 맡습니다. 상품 DB에 벡터를 함께 저장하고, Modal GPU는 대량 등록에, Voyage API는 글을 벡터로 바꾸는 데 사용합니다. 왼쪽은 비용과 역할을 비교하기 위한 한 가지 구성입니다. 모든 검색 시스템에 저 서비스들이 필요한 것은 아닙니다.

상품 1만 개와 월 10만 번의 검색어 검색을 가정하면, GPU와 임베딩 API 사용료는 첫 등록 약 1.70달러, 이후 월 약 0.24달러로 계산됩니다. 검색 서버와 DB 운영비를 뺀 값이며 실측 비용은 아닙니다. 이 계산이 성립하는 조건은 뒤에서 따져보겠습니다. 먼저 ‘흰색 운동화’가 어떤 단계를 거쳐 검색 결과가 되는지 따라가 보죠.

## 글자가 달라도 같은 종류의 상품을 찾아야 합니다

비교 기준은 ‘흰색’과 ‘운동화’가 상품명에 모두 들어 있어야 찾는 단순한 검색입니다. 운동화 A, 같은 사진을 쓰는 A 복제, 화이트 스니커즈 B, 흰색 신발끈 네 상품을 놓고 이 규칙을 적용했습니다.

  <div class="fig" data-fig="keyword" role="group" aria-label="상품 네 개의 이름에서 흰색과 운동화라는 글자를 차례로 찾습니다. 흰색 운동화 A와 A 복제는 찾고, 화이트 스니커즈 B와 흰색 신발끈은 못 찾습니다. 마지막 줄의 사진으로 찾기는 검색할 수 없다고 표시됩니다."></div>

운동화 A와 A 복제는 찾지만 스니커즈 B는 빠집니다. 단어가 같아야 한다는 조건 때문입니다. 동의어 사전을 붙이면 이 예시는 해결할 수 있지만, 사전에 없는 표현과 사진 입력까지 처리하려면 다른 비교 방법도 필요합니다. 그래서 글의 뜻과 사진의 생김새를 숫자로 바꿔 비교하는 검색을 더합니다.

## 검색은 두 단계로 나눴습니다

검색 결과를 만드는 과정은 두 단계입니다. 먼저 관련 있어 보이는 상품을 모으고, 그 안에서 보여줄 순서를 정합니다.

- 후보 모으기(Retrieval): 전체 상품 중 관련 있어 보이는 상품을 넉넉히 가져옵니다.
- 순서 정하기(Ranking): 모은 후보만 놓고 보여줄 순서를 정합니다.

상품이 1만 개여도 후보 모으기가 수백 개만 남기면, 순서 정하기는 그 수백 개만 계산하면 됩니다.

<figure class="fig-figure">
  <div class="fig" data-fig="funnel" role="group" aria-label="전체 상품에서 후보, 순서 정하기, 검색 결과로 갈수록 상품 수가 줄어듭니다. 전체 상품 안의 빨간 점은 후보로 넘어가지 못하고 막힙니다."></div>
  <figcaption>후보 모으기와 순서 정하기 (점의 개수는 설명용)</figcaption>
</figure>

빨간 점은 후보에서 빠진 상품입니다. 이후 단계는 후보만 다루므로, 빠진 상품을 점수 보정으로 되살릴 수 없습니다. 후보 단계에서는 원하는 상품을 놓치지 않는 것이 중요하고, 순위 단계에서는 찾은 상품 중 무엇을 먼저 보여줄지가 중요합니다. 두 단계가 잘못됐을 때 확인할 곳도 달라집니다.

## 사진은 숫자 목록으로 바꿔서 비교합니다

사진 검색의 후보를 모으려면 두 사진의 생김새를 비교해야 합니다. 픽셀을 그대로 비교하면 같은 운동화도 각도나 조명이 바뀔 때 값이 크게 달라집니다. 배경색이 비슷한 서로 다른 물건을 가깝게 볼 수도 있습니다.

이미지 모델은 사진 한 장을 숫자 목록으로 바꿉니다. 이 목록이 벡터이고, 입력의 특징을 벡터로 표현한 것을 임베딩(embedding)이라고 부릅니다. 저희가 쓰는 [SigLIP](https://arxiv.org/abs/2303.15343)은 사진과 설명 글의 관계를 학습한 모델입니다. 그 모델이 만든 이미지 벡터를 비교해, 픽셀 위치가 달라도 비슷한 특징을 가진 사진을 찾습니다.

<figure class="fig-figure">
  <div class="fig" data-fig="embedding" role="group" aria-label="운동화 A, 같은 운동화를 다른 각도에서 찍은 사진, 신발끈 사진이 차례로 이미지 모델을 거쳐 숫자 여섯 개로 된 목록이 됩니다. 운동화 A와 다른 각도 사진의 유사도는 0.99, 운동화 A와 신발끈의 유사도는 0.59로 표시됩니다."></div>
  <figcaption>사진을 벡터로 바꾸고 비교하는 원리 (설명용 6차원 벡터, 실제 모델 출력이 아님)</figcaption>
</figure>

그림에서는 원리를 보이려고 숫자 여섯 개짜리 벡터를 만들었습니다. 다른 각도의 운동화는 유사도 0.99, 신발끈은 0.59가 되도록 계산한 예시이며, SigLIP으로 이 사진들을 측정한 결과는 아닙니다. 실제 모델의 벡터도 각 숫자를 ‘색’, ‘모양’처럼 하나씩 해석해서 쓰지는 않습니다. 검색에서는 두 벡터가 얼마나 가까운지를 비교합니다.

SigLIP은 공개된 모델을 내려받아 직접 실행합니다. 모델 API 호출료는 없지만 실행할 CPU나 GPU 자원은 필요합니다. 아래는 사진 한 장을 벡터로 바꾸는 부분만 남긴 코드입니다. 라이브러리 import, 이미지 로딩과 오류 처리는 생략했습니다.

```python
model, _, preprocess = open_clip.create_model_and_transforms(
    "ViT-B-16-SigLIP", pretrained="webli"
)
model.eval()

image_tensor = preprocess(image.convert("RGB")).unsqueeze(0)
with torch.no_grad():
    vector = model.encode_image(image_tensor)
    vector = vector / vector.norm(dim=-1, keepdim=True)
```

`preprocess`가 사진의 크기와 입력 형식을 맞추고, `encode_image`가 벡터를 만듭니다. 마지막 줄은 벡터의 길이를 1로 맞추는데, 이렇게 하면 뒤에서 설명할 유사도를 같은 자리의 숫자끼리 곱해서 더하는 방식으로 계산할 수 있습니다.

비교할 상품 사진과 검색 사진에는 같은 모델과 전처리를 적용해야 합니다. 다른 모델의 벡터는 각 숫자가 나타내는 기준이 다르므로 차원 수가 같아도 그대로 비교할 수 없습니다. 텍스트는 별도 모델을 쓰기 때문에 사진 벡터와 다른 컬럼에 저장합니다.

## 사진은 등록할 때 한 번만 읽습니다

벡터를 만들 수 있게 됐다고 검색할 때마다 모든 상품 사진을 모델에 넣을 필요는 없습니다. 같은 사진에는 같은 계산을 반복하게 되니까요. 상품을 등록할 때 벡터를 저장해 두면, 사진 검색에서는 사용자가 올린 한 장만 새로 바꾸면 됩니다. 상품 사진이나 모델을 바꿀 때는 저장된 벡터도 다시 만들어야 합니다.

  <div class="fig" data-fig="flow" role="group" aria-label="위쪽 상품 등록 단계에서 사진 여덟 장이 GPU의 이미지 모델을 거쳐 벡터가 되고 products 표에 저장됩니다. 아래쪽 검색 요청 단계에서는 사진 한 장만 CPU의 이미지 모델을 거쳐 벡터가 되고, 저장된 벡터 여덟 개와 비교해 가장 가까운 세 개를 고릅니다."></div>
  <figcaption>등록할 때와 검색할 때의 흐름 (모식도, 예시 벡터로 계산)</figcaption>
</figure>

등록 단계의 상품 여덟 장은 모두 모델을 거칩니다. 그 뒤 검색 #1과 #2에서는 검색 사진만 바뀌고, 저장된 상품 벡터는 다시 사용됩니다. 반복되는 검색에서 상품 이미지 모델 계산을 덜어낸 것입니다.

상품 수에 따라 그려 보면 차이가 더 분명합니다. 가로축은 상품 수, 세로축은 검색 한 번에 모델이 처리하는 사진 수입니다.

<figure class="fig-figure">
  <div class="fig" data-fig="per-search" role="group" aria-label="가로축 상품 수가 0에서 10만으로 늘어날 때, 검색마다 전부 바꾸는 방식은 모델에 넣는 사진 수가 10만 장까지 늘고, 미리 바꿔 두는 방식은 1장에 머뭅니다."></div>
  <figcaption>검색 한 번에 모델이 처리하는 사진 수 (측정값이 아닌 정의상 개수)</figcaption>
</figure>

상품이 10만 개여도 검색 시 모델에 넣는 사진은 한 장입니다. 이 그래프는 모델에 넣는 사진 수를 비교한 것이며, 검색시간이 상품 수와 무관하다는 뜻은 아닙니다. 저장된 벡터에서 가까운 상품을 찾는 DB 작업은 여전히 남아 있습니다.

검색 서버는 그 한 장을 CPU로 처리합니다. 사진을 한꺼번에 많이 등록할 때는 Modal의 T4 GPU를 빌려 씁니다. 두 실행 경로에서 같은 모델과 전처리를 적용하므로 벡터를 비교할 수 있습니다. 이 역할 분담으로 검색 서버에 GPU를 상시 두지 않지만, CPU의 사진 처리시간과 동시 검색 한도는 별도 측정이 필요합니다.

검색어까지 합쳐 각 작업이 언제, 어디서 실행되는지 정리하면 이렇습니다.

| 하는 일 | 언제 | 어디서 |
| --- | --- | --- |
| 상품 사진 → 벡터 | 미리, 한 번 | Modal의 T4 GPU (대량 등록) |
| 상품명과 키워드 → 벡터 | 미리, 한 번 | Voyage API |
| 검색 사진 → 벡터 | 사진 검색마다 | 검색 서버의 CPU |
| 검색어 → 벡터 | 검색어 검색마다 | Voyage API |
| 후보 모으기 | 검색마다 | PostgreSQL |
| 순서 정하기 | 검색어 검색마다 | 검색 서버 |

검색어 검색에서는 매번 Voyage API가 입력을 벡터로 바꿉니다. 이 경우 직접 모델을 운영할 자원 대신 API 사용료와 외부 호출시간이 들어갑니다.

## 가까운 상품은 PostgreSQL이 찾습니다

상품 벡터를 저장했으니 검색 벡터와 가까운 것을 골라야 합니다. 여기서는 두 벡터의 방향을 비교하는 코사인 유사도를 씁니다. 두 화살표가 같은 방향이면 1, 직각이면 0, 정반대면 -1입니다. 앞에서 벡터의 길이를 맞춘 것도 이 비교를 계산하기 위해서입니다.

아래는 숫자가 두 개뿐인 벡터로 그린 예시입니다. 검은 화살표가 검색 벡터이고, 오른쪽 목록은 P, Q, R과의 유사도를 큰 순서로 보여줍니다. 점선은 두 벡터의 한가운데예요.

<figure class="fig-figure">
  <div class="fig" data-fig="cosine" role="group" aria-label="반원 위에 P(20도), Q(80도), R(150도) 방향의 벡터가 있고, 검색 벡터가 15도에서 165도까지 돌아갑니다. 오른쪽 목록은 각 벡터와의 코사인 유사도를 큰 순서로 보여주며, 검색 벡터가 50도를 넘으면 Q가 P를 앞서고 115도를 넘으면 R이 Q를 앞섭니다."></div>
  <figcaption>각도와 코사인 유사도 (모델 출력이 아닌 2차원 예시)</figcaption>
</figure>

검색 벡터가 P와 Q의 한가운데인 50°를 넘으면 Q가 P를 앞서고, 115°를 넘으면 R이 Q를 앞섭니다. 실제 벡터는 숫자가 수백 개라 그림으로 그릴 수 없지만, 계산 방법은 같아요.

그럼 숫자가 수백 개일 때는 어떻게 계산할까요? 앞에서 벡터 길이를 1로 맞춘 게 여기서 쓰입니다. 길이가 모두 1이면, 같은 자리의 숫자끼리 곱해서 모두 더한 값(내적)이 곧 코사인 유사도입니다.

<figure class="fig-figure">
  <div class="fig" data-fig="dot" role="group" aria-label="길이가 1인 검색 벡터와 상품 벡터의 숫자 여섯 개를 같은 자리끼리 곱해 0.25, 0.07, 0.23, 0.01, 0.25, 0.17을 만들고, 모두 더한 0.98이 코사인 유사도로 표시됩니다. 반올림 전 값으로 계산하고 소수 둘째 자리까지 표시합니다."></div>
  <figcaption>같은 자리끼리 곱해서 더하기 (정규화한 예시 벡터, 반올림 전 값으로 계산해 소수 둘째 자리까지 표시)</figcaption>
</figure>

여섯 자리를 곱한 값은 표시한 자리에서 0.25, 0.07, 0.23, 0.01, 0.25, 0.17이고 합은 0.98입니다. 실제 계산에는 반올림 전의 정규화한 벡터를 사용합니다. 숫자가 수백 개여도 같은 자리끼리 곱해서 더하는 방법은 같습니다.

저희는 상품 테이블에 벡터 컬럼을 추가하고 PostgreSQL에서 가까운 상품을 찾습니다. pgvector 확장을 설치하면 벡터를 저장하고 거리를 계산할 수 있습니다. 아래는 사진 검색의 거리 정렬을 보여주기 위해 조회 컬럼을 줄인 SQL입니다. `:query_vector`와 `:candidate_limit`에는 호출하는 코드에서 검색 벡터와 후보 개수를 넣습니다.

```sql
SELECT id, 1 - (embedding <=> :query_vector) AS similarity
FROM products
WHERE embedding IS NOT NULL
ORDER BY embedding <=> :query_vector
LIMIT :candidate_limit;
```

`<=>`는 두 벡터의 코사인 거리를 구하는 연산자입니다. 거리는 `1 - 유사도`라서, 유사도가 0.97이면 거리는 0.03이에요. 거리가 작은 순서로 정렬해서 앞에서부터 정해진 개수만 가져옵니다. 상품 여덟 개로 보면 이렇습니다.

<figure class="fig-figure">
  <div class="fig" data-fig="pgvector" role="group" aria-label="상품 여덟 개에 거리가 하나씩 채워진 뒤 거리 순으로 다시 정렬됩니다. 운동화 A와 A 복제가 0.03, 스니커즈 B가 0.12로 가장 가깝고, LIMIT 3 선 아래의 신발끈, 샌들 C, 슬리퍼 D, 모자 F, 머그컵 E는 흐려집니다."></div>
  <figcaption>ORDER BY 거리 LIMIT 3 (거리는 예시 값, 실제 개수는 :candidate_limit)</figcaption>
</figure>

같은 사진을 쓰는 운동화 A와 A 복제는 같은 거리로 나란히 들어옵니다. DB는 이 단계에서 가까운 상품을 찾을 뿐, 같은 사진을 몇 개 보여줄지는 결정하지 않습니다. LIMIT 아래의 상품은 후보에서 빠지므로 뒤의 순위 계산에도 들어오지 않습니다.

상품 정보와 벡터가 같은 행에 있으므로 별도 저장소와 삭제 상태를 맞출 필요가 없습니다. 상품 행을 지우면 벡터도 지워지고, 벡터가 아직 없는 행은 `WHERE embedding IS NOT NULL`로 제외됩니다. 등록 후 벡터 생성이 끝나기 전에는 그 상품이 이 검색에서 빠진다는 조건도 생깁니다. 연산자와 계산식은 [pgvector 문서](https://github.com/pgvector/pgvector#querying)에 정리되어 있습니다.

다만 유사도 0.9가 ‘같은 상품일 확률 90%’라는 뜻은 아닙니다. 모양이 비슷한 다른 상품이나 배경이 비슷한 사진도 높게 나오죠.

## 검색어는 두 번 찾아서 합칩니다

사진 검색은 저장된 이미지 벡터와 비교합니다. 검색어 검색은 상품명과 키워드를 미리 만든 텍스트 벡터와 비교합니다. 텍스트 모델은 Voyage의 `voyage-multilingual-2`이며, 검색어에도 같은 모델을 사용합니다. 사진과 글의 벡터를 섞어서 비교하는 구성은 아닙니다.

글자를 벡터로 비교하면 표기가 달라도 뜻이 비슷한 상품이 가까이 옵니다. 검색어 주변에 무엇이 모이는지 개념도로 보면 이렇습니다.

  <div class="fig" data-fig="text-space" role="group" aria-label="흰색 운동화라는 검색어 주변의 원 안에 흰색 운동화 A, A 복제, 화이트 스니커즈 B, 흰색 신발끈이 있고, 원 밖 멀리에 검정 구두, 가죽 지갑, 흰색 머그컵이 있습니다."></div>
  <figcaption>검색어 벡터 근처의 상품 (개념도, 실제 벡터를 옮긴 그림이 아님)</figcaption>

이 개념도는 ‘화이트 스니커즈’처럼 표기가 다른 상품도 뜻으로 찾는 역할을 보여줍니다. 동시에 ‘흰색 신발끈’처럼 관련은 있지만 찾는 종류가 아닌 상품도 가까이 올 수 있습니다. 실제 모델에서 이 상품들의 거리를 측정한 그림은 아니며, 벡터 검색이 정확한 상품 종류를 보장한다는 뜻도 아닙니다.

벡터 검색은 가까운 상품을 정해진 개수만 가져옵니다. 상품명에 검색어가 그대로 들어 있어도 이 개수 밖으로 밀리면 후보에서 빠집니다. 이를 보완하려고 검색어 검색에서는 두 목록을 합칩니다.

- 벡터로 찾기: 검색어 벡터와 가까운 상품
- 단어로 찾기: 이름이나 키워드에 검색어 단어가 들어 있는 상품

아래 예시에서는 ‘화이트’가 ‘흰색’과, ‘스니커즈’가 ‘운동화’와 같은 말로 묶여 있고, 벡터로는 두 개만 가져온다고 가정했습니다.

<figure class="fig-figure">
  <div class="fig" data-fig="candidates" role="group" aria-label="검색어 흰색 운동화에 대해 상품 네 개가 있습니다. 벡터로 찾으면 유사도가 높은 신발끈과 운동화 A만 가져오고, 이때 스니커즈 B는 후보에 없다고 표시됩니다. 이어서 단어로 찾으면 운동화 A, A 복제, 스니커즈 B를 가져오고, 합친 후보에는 네 상품이 한 번씩 들어갑니다."></div>
  <figcaption>벡터로 찾기와 단어로 찾기 (유사도는 설명용 값, 실제 후보 수는 훨씬 많음)</figcaption>

스니커즈 B의 예시 유사도는 0.920으로 네 상품 중 가장 낮습니다. 벡터로 두 개만 찾으면 빠지지만, 동의어를 적용한 단어 검색에서는 들어옵니다. 두 목록을 합치면 네 상품이 모두 후보가 되고, 양쪽에서 찾은 운동화 A는 한 번만 남습니다. 신발끈도 후보에 있는데요. 이 단계에서는 관련 상품을 확보하고, 부속품을 뒤로 내리는 일은 순위 단계에서 합니다.

구현에서는 각 방법이 `max(200, 요청한 결과 수 × 4)`개까지 가져옵니다. 결과 20개를 요청하면 각각 최대 200개, 합치면 최대 400개입니다. 결과 100개를 요청하면 각각 최대 400개가 됩니다. 실제 후보 수는 일치하는 상품 수와 두 목록의 중복에 따라 줄어듭니다. 아래는 SQL의 목록 결합 구조만 남긴 의사 코드입니다.

```sql
WITH semantic AS (
    -- 텍스트 벡터가 가까운 상품 ID
), lexical AS (
    -- 상품명과 키워드가 일치하는 상품 ID
), candidates AS (
    SELECT id FROM semantic
    UNION
    SELECT id FROM lexical
)
-- 후보의 이름, 키워드, 벡터를 가져와 순위 계산에 사용
```

`UNION`은 두 목록의 상품 ID를 중복 없이 합칩니다. 단어 검색에 쓰는 동의어는 ‘운동화’와 ‘스니커즈’처럼 사전에 묶어 둔 것만 적용됩니다. 짧은 검색어에는 단어 경계도 확인합니다. ‘아이’라는 글자만 찾으면 ‘아이스’에 걸리기 때문에, 일부 짧은 단어는 독립된 단어로 있는지를 봅니다.

후보를 늘리면 순위를 매길 기회가 생기는 상품도 늘지만, DB에서 읽을 행과 서버의 계산량도 늘어납니다. `200`과 `4배`는 이 구현의 설정값이며 다른 상품군에서도 충분하다는 측정 결과는 없습니다. 원하는 상품이 후보에 들어오는지와 후보 처리시간을 함께 확인하며 조정할 값입니다.

## 신발끈은 점수로 내립니다

후보 네 개를 유사도만으로 정렬하면 흰색 신발끈이 먼저 나옵니다. 예시 유사도가 0.995로 가장 높기 때문입니다. ‘관련 있는 물건’ 가운데 ‘검색한 종류의 물건’을 앞에 놓으려면 단어와 종류를 함께 봐야 합니다.

- 단어 일치: 검색어 단어가 몇 개 맞는가. ‘흰색 운동화’는 두 묶음이라 둘 다 맞으면 1, 하나만 맞으면 0.5입니다.
- 종류 일치: 상품 종류가 맞는가. 신발끈은 운동화와 관련은 있어도 운동화는 아니니 0입니다.

검색어에서 상품 종류를 알아낸 경우에는 세 값을 다음 가중치로 합칩니다. 점수 계산 부분만 옮긴 코드입니다.

```python
score = (
    0.60 * cosine_similarity
    + 0.25 * matched_groups / total_groups
    + 0.15 * type_match
)
```

운동화 A는 0.60 × 0.98 + 0.25 × 1 + 0.15 × 1 = 0.988이고, 신발끈은 0.60 × 0.995 + 0.25 × 0.5 + 0.15 × 0 = 0.722입니다. 막대 하나가 상품 하나이고, 파란 조각이 유사도, 보라 조각이 단어, 초록 조각이 종류예요.

유사도에 해당하는 파란 조각은 네 상품이 비슷합니다. 단어와 종류를 더한 뒤에는 신발끈의 점수가 운동화보다 낮아집니다. 이 가중치가 모든 검색어에서 최적이라는 뜻은 아닙니다. 종류를 알아내지 못한 검색어에는 다른 가중치를 사용합니다.

점수를 비교하기 전에 우선순위 그룹도 나눕니다. 상품번호가 정확히 맞는 상품, 검색어 단어가 모두 맞는 상품, 종류만 맞는 상품, 나머지 순입니다. 높은 그룹을 먼저 보여주고 같은 그룹 안에서 점수로 비교합니다. 상품번호가 정확히 맞는 결과를 벡터 유사도 차이 때문에 뒤로 보내지 않기 위한 규칙입니다.

## 같은 사진은 뒤로 미룹니다

신발끈을 내린 뒤에도 운동화 A와 A 복제가 1, 2위입니다. 같은 사진을 쓰는 상품들이 비슷한 점수로 앞에 모이면 첫 화면에서 볼 수 있는 상품의 종류가 줄어듭니다.

그래서 결과를 하나씩 고르면서, 이미 고른 상품과 많이 겹치는 후보는 점수를 깎습니다. 겹치는 정도는 세 가지로 봅니다.

- 벡터: 두 상품의 벡터가 얼마나 비슷한가
- 이름: 상품명에 같은 단어가 얼마나 있는가
- 사진: 같은 사진 주소를 쓰는가

이름이 겹치는 정도는 Jaccard 유사도로 잽니다. 두 이름에 함께 나오는 단어 수를, 두 이름에 나온 단어를 중복 없이 모은 수로 나눈 값이에요. 사진이 같으면 이름과 상관없이 겹침을 1로 봅니다.

‘흰색 운동화 A’와 ‘흰색 운동화 A 복제’는 단어 넷 중 셋이 겹쳐 0.75입니다. ‘화이트 스니커즈 B’와는 글자 그대로 겹치는 단어가 없어 0입니다. 이 예시는 이름의 단어 집합을 비교하며, 후보 검색에 쓰던 동의어를 적용한 결과는 아닙니다.

이제 같은 네 후보를 세 번 줄 세워 볼게요. ① 유사도만, ② 단어와 종류 반영, ③ 겹침 감점 순서입니다.

<figure class="fig-figure">
  <div class="fig" data-fig="ranking" role="group" aria-label="같은 네 후보를 세 단계로 정렬합니다. 유사도만 쓰면 신발끈, 운동화 A, A 복제, 스니커즈 B 순서입니다. 단어와 종류를 반영하면 운동화 A 0.988, A 복제 0.982, 스니커즈 B 0.952, 신발끈 0.722 순서가 됩니다. 겹침 감점을 적용하면 운동화 A를 고른 뒤 A 복제에서 0.080, 스니커즈 B에서 0.039, 신발끈에서 0.050을 깎아 스니커즈 B가 2위, A 복제가 3위가 됩니다."></div>
  <figcaption>유사도, 단어·종류 점수, 겹침 감점을 적용한 순서 (예시 데이터로 계산)</figcaption>
</figure>

③에서 B와 A 복제가 자리를 바꿉니다. 운동화 A를 먼저 고르면 같은 사진을 쓰는 A 복제는 0.080이 깎이고, 사진도 이름도 다른 B는 0.039가 깎여요. 원래 점수는 A 복제 0.982, B 0.952로 0.030 차이였는데, 깎인 양의 차이(0.041)가 더 커서 B가 앞섭니다.

이미 고른 상품과 비교해 감점을 갱신하는 부분입니다. 후보 선택과 반복문은 생략했습니다.

```python
overlap = max(name_jaccard, float(same_image))
penalty = strength * (0.5 * vector_similarity + 0.5 * overlap)
redundancy = max(previous_redundancy, penalty)
priority = tier + score - redundancy
```

`overlap`은 이름의 겹침과 동일 사진 여부 중 큰 값입니다. 벡터 유사도와 이 값을 절반씩 반영한 뒤 `strength`를 곱해 감점합니다. 이미 고른 상품이 여러 개라면 `redundancy`에는 그중 가장 큰 감점을 남깁니다. 모든 감점을 합산하는 방식은 아닙니다.

`strength`는 검색어 묶음이 하나면 0.3, 여러 개면 0.08입니다. ‘흰색 운동화’ 예시는 두 묶음이라 0.08을 썼습니다. 이 값도 상품군과 검색어에 맞춰 확인할 설정입니다. 같은 사진이 같은 상품을 보장하지 않으므로 후보를 삭제하지 않고 우선순위를 낮춥니다. 얼마나 뒤로 가는지는 다른 후보의 점수에 따라 달라집니다.

## 월 0.24달러는 임베딩 API 사용료입니다

이 구성은 GPU를 대량 등록 때 사용하고, 검색어가 들어올 때마다 임베딩 API를 호출합니다. 이 두 사용료를 가정에 따라 계산해 보겠습니다. 실제 사용량이나 청구액이 아니며, 단가는 2026년 10월 4일 공식 요금표에서 다시 확인했습니다.

| 항목 | 가정 또는 단가 | 근거 |
| --- | --- | --- |
| 상품 | 1만 개, 상품마다 사진 1장 | 예시 |
| 검색어 검색 | 한 달 10만 번, 검색어 하나에 20토큰 | 계산용 가정 |
| 상품명과 키워드 | 상품 하나에 50토큰 | 예시 |
| GPU로 사진 한 장 처리 | 1초 | 계산용 가정, 실제 처리시간은 미측정 |
| Modal T4 GPU (실제 사용) | 1초에 0.000164달러 | [Modal 요금표](https://modal.com/pricing) |
| Voyage voyage-multilingual-2 (실제 사용) | 100만 토큰에 0.12달러 | [Voyage 요금표](https://docs.voyageai.com/docs/pricing) |

계산은 단순합니다.

- GPU를 한 달 내내 켜 두면: 0.000164달러 × 60초 × 60분 × 24시간 × 30일 = 425.09달러
- 첫 등록(사진): 사진 1만 장 × 1초 × 0.000164달러 = 1.64달러
- 첫 등록(상품명): 1만 개 × 50토큰 = 50만 토큰 → 0.06달러
- 매달(검색어): 10만 번 × 20토큰 = 200만 토큰 → 0.24달러

첫 등록의 이미지 계산 1.64달러와 상품명 임베딩 0.06달러를 합치면 1.70달러입니다. 이후 상품을 추가하거나 바꾸지 않는 달에는 검색어 200만 토큰의 API 사용료가 0.24달러입니다. 상품을 추가하면 등록 사용료도 다시 발생합니다.

왼쪽 막대는 T4를 30일 내내 할당하고 Pinecone Standard를 사용하는 경우입니다. 이 조건에서는 검색이 없어도 해당 비용이 나옵니다. GPU를 필요할 때만 할당하거나 다른 DB 요금제를 쓰면 비교 값도 바뀝니다. 위 막대의 차이를 이 구현의 실제 절감액으로 읽을 수는 없습니다.

별도 벡터 DB를 두지 않아도 PostgreSQL의 저장 공간은 필요합니다. pgvector의 `vector` 타입은 벡터 하나에 ‘4 × 차원 + 8’바이트를 씁니다. 사진 벡터 768차원은 3,080바이트, 텍스트 벡터 1,024차원은 4,104바이트입니다. 둘을 합쳐 상품 1만 개에 약 72MB이며, 행과 인덱스 등의 추가 공간은 제외한 벡터 자체의 크기입니다. [pgvector의 타입 정의](https://github.com/pgvector/pgvector#vector-type)를 기준으로 계산했습니다.

이 계산에서 뺀 것도 있습니다.

- 무료 사용량과 크레딧: 적용 가능한 잔여량은 계정 상태에 따라 다릅니다. Modal Starter의 월 30달러 크레딧과 Voyage의 무료 토큰은 계산에 넣지 않았습니다.
- GPU 실행의 부대비용: 사진당 1초만 가정했습니다. 모델 로딩과 준비시간, 함께 쓰는 CPU·메모리, 저장소와 네트워크 사용료 등은 별도입니다.
- 검색 서버와 PostgreSQL: 사진 검색의 CPU 계산, 벡터 조회와 순위 계산에 쓰는 자원은 무료가 아닙니다. 기존 자원의 여유 안에서 처리할 수 있는지는 측정하지 않았습니다.
- 비교 구성의 다른 비용: 검색 서버, 검색 엔진, 임베딩을 만드는 비용 등은 합산하지 않았습니다. 완전한 두 시스템의 총운영비 비교가 아닙니다.

## 규칙을 관리하고 검색 한도를 확인해야 합니다

별도 검색 서비스의 역할 일부를 DB 조회와 서버 코드로 옮겼으므로 그 동작을 직접 확인해야 합니다. 동의어 사전, 상품 종류, 점수 가중치와 감점은 사람이 관리하는 규칙입니다. 하나를 바꾸면 검색어마다 결과가 다르게 바뀔 수 있으므로 같은 상품과 검색어를 놓고 다음 항목을 확인해야 합니다.

- 종류가 맞는 상품이 위에 있는가
- 신발끈 같은 부속품이 앞에 나오지 않는가
- ‘아이’가 ‘아이스’에 걸리지 않는가
- 비슷한 상품이 결과를 다 차지하지 않는가

규칙을 바꿀 때는 예전 검색어도 다시 돌려 봐야 합니다.

검색어 검색은 매번 Voyage API를 거치므로 외부 API의 응답시간과 가용성도 영향을 줍니다. 단가 계산만으로 검색 응답시간이나 장애 시 동작까지 확인한 것은 아닙니다.

‘화이트 스니커즈 B’가 보이지 않는다면 먼저 후보 목록을 확인합니다. 후보에 없으면 벡터와 단어 검색, 후보 개수를 보고, 후보에 있는데 뒤로 밀렸다면 종류 판별과 점수, 감점을 봅니다. 단계별로 상품 ID와 점수를 확인하면 고칠 규칙을 좁힐 수 있습니다.

CPU의 사진 처리시간, 동시 검색을 감당하는 정도, 대량 등록 속도는 아직 측정하지 않았습니다. 현재 대량 등록은 사진을 한 장씩 처리합니다. 여러 장을 묶는 방식의 효과도 같은 조건에서 재야 알 수 있습니다. 본문의 예시 점수와 비용으로 이 한도를 대신할 수는 없습니다.

처음의 두 입력은 서로 다른 경로로 해결합니다. 사진은 같은 이미지 모델의 벡터로 비교하고, ‘흰색 운동화’라는 글은 텍스트 벡터와 단어 검색으로 후보를 모읍니다. 그 안에서 신발끈을 내리고 같은 사진이 앞에 모이지 않도록 점수를 보정합니다. GPU를 등록 때 빌려 쓰고 벡터를 상품 DB에 저장하면 GPU 서버와 별도 벡터 DB를 상시 운영하지 않고 이 흐름을 만들 수 있습니다. 실제 상품군에서 원하는 결과를 찾는지, 그리고 어느 규모까지 이 자원으로 처리할 수 있는지가 이 구성을 적용할 때 확인할 조건입니다.
