`git log`를 열었는데 `수정`, `fix`, `test2` 같은 메시지가 줄지어 있을 때의 막막함을 안다. 그 커밋을 쓴 사람이 바로 나였다는 사실이 더 막막하다.

## 무엇이 아니라 왜

diff를 보면 **무엇이** 바뀌었는지는 누구나 알 수 있다. 코드가 알려주지 못하는 건 **왜** 바꿨는지다. 그래서 메시지는 변경 내용의 요약이 아니라 이유를 적는 자리라고 생각하기로 했다.

```bash
# 이런 메시지는 나중에 아무 도움이 안 된다
git commit -m "수정"

# 이유가 남아 있으면 반년 뒤에도 읽힌다
git commit -m "주문 취소 시 재고를 되돌리지 않던 문제 수정

취소 API가 결제 상태만 바꾸고 재고 테이블은 건드리지 않아
취소된 주문의 수량이 계속 차감된 채로 남았다."
```

## 내가 지키는 세 가지

- 첫 줄은 오십 자 안에서, 결과가 드러나게 쓴다
- 둘째 줄은 비우고, 셋째 줄부터 이유와 맥락을 적는다
- 한 커밋에는 한 가지 이유만 담는다

마지막 규칙이 가장 어렵다. 작업하다 보면 눈에 띈 것들을 한꺼번에 고치고 싶어진다. 그럴 때는 `git add -p`로 조각을 나눠서 담는다. 귀찮지만, 나중에 `git bisect`가 범인을 정확히 짚어 줄 때 이 수고를 보상받는다.

> 커밋 메시지는 코드 리뷰어보다 먼저 미래의 나를 위한 글이다.

오늘도 커밋 하나를 쓰기 전에 잠깐 멈춘다. 반년 뒤의 내가 이 줄을 읽는다면, 무엇이 궁금할까.
