처음 회사에 들어가서 가장 무서웠던 건 새로운 기술이 아니라 **남이 쓴 코드**였다. 수천 줄짜리 파일을 열면 어디서부터 읽어야 할지 막막했고, 이해되지 않는 부분에서는 나 자신이 부족한 사람처럼 느껴졌다.

몇 년이 지나고 나서야 알았다. 코드는 위에서 아래로 읽는 글이 아니라, **지도를 보듯이** 읽는 것이었다.

## 입구부터 찾는다

먼저 프로그램이 시작되는 곳을 찾는다. 웹 서버라면 요청이 들어오는 곳, 명령어 도구라면 `main` 함수다. 전체를 이해하려 하지 않고, 한 가지 흐름만 끝까지 따라간다.

```bash
# 이 함수는 어디서 불리고 있을까?
grep -rn "createOrder" src/

# 이 파일은 언제, 왜 이렇게 바뀌었을까?
git log --follow -p -- src/order.js
```

두 줄이면 충분하다. 누가 어디서 이 함수를 쓰는지 알면 코드의 역할이 절반은 보인다.

## 모르는 곳은 표시만 하고 지나간다

이해되지 않는 부분마다 멈추면 끝까지 가지 못한다. 그래서 물음표만 적어 두고 일단 넘어간다. 나중에 전체 그림이 잡히면 대부분의 물음표는 저절로 풀려 있다.

- 처음부터 다 이해하려 하지 않는다
- 한 번에 한 가지 흐름만 따라간다
- 읽으면서 작은 메모를 남긴다

## 읽는 일도 쓰는 일이다

시간이 지나 보니 잘 읽는 사람이 잘 쓰는 사람이 되었다. 남의 코드를 읽으며 "왜 이렇게 했을까"를 자주 물었더니, 내 코드를 쓸 때도 "누가 읽을까"를 먼저 생각하게 되었다.

천천히 읽는 것이 결국 가장 빠른 길이었다.
