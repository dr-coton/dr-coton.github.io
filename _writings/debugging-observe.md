버그를 만나면 나는 곧장 범인을 지목하곤 했다. "분명 캐시 문제일 거야." 그러고는 한 시간 동안 캐시 코드만 들여다봤는데, 결국 원인은 전혀 다른 곳에 있었다.

## 추측은 빠르고, 틀리기도 빠르다

머릿속 가설은 그럴듯해서 위험하다. 확인하지 않은 가설 위에 다음 가설을 쌓으면, 처음부터 방향이 틀렸다는 걸 알아챌 때쯤엔 이미 멀리 와 있다.

그래서 순서를 바꿨다. 가설을 세우기 전에 **실제로 무슨 일이 일어나는지부터 본다.**

1. 버그를 항상 재현할 수 있는 가장 작은 입력을 찾는다
2. 그 입력이 지나가는 길에 값을 찍어 본다
3. 기대한 값과 실제 값이 처음 달라지는 지점을 찾는다
4. 그제야 왜 달라졌는지 생각한다

## 값을 찍어 본다

거창한 도구보다 로그 한 줄이 먼저다.

```js
function applyDiscount(price, coupon) {
  console.log('입력', { price, coupon });
  const rate = coupon?.rate ?? 0;
  const result = price - price * rate;
  console.log('결과', { rate, result });
  return result;
}
```

이렇게 찍어 보고 나서야 `rate`가 `0.1`이 아니라 문자열 `"10"`으로 들어오고 있다는 걸 알았다. 캐시는 아무 잘못이 없었다.

> 짐작하지 말고, 먼저 본다.

## 찾고 나면 지운다

원인을 찾았다면 찍어 둔 로그는 지운다. 그리고 재현하던 그 입력을 테스트로 남긴다. 같은 버그를 두 번 만나는 일만큼 억울한 것도 없으니까.

디버깅이 예전만큼 무섭지 않다. 이제는 탐정이 되기보다, 관찰자가 되려고 한다.
