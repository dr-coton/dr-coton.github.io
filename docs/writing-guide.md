# 꼬박사의 연구노트 글쓰기 가이드

이 문서는 글을 작성하고 수정하는 사람과 에이전트를 위한 내부 편집 지침이다. 블로그 본문이 아니다. 사용자와 함께 수정하면서 구체적인 취향을 축적한다. 현재 사용자의 요청이 이 문서보다 우선한다.

## 확인된 취향과 참고 글

사용자는 상투적인 소개, 과한 수식, 추상적인 교훈이 반복되는 문구를 선호하지 않는다. 어렵고 AI처럼 들리는 문장도 피한다. '배치로 정해진다', '외부에 기대는 것', '대신 떠안는 것' 같은 추상 명사 대신 '미리 바꿔 둔다', '검색할 때마다 호출한다'처럼 쉬운 동사로 쓴다. 용어는 처음 나올 때 일상어로 풀고(벡터 = 숫자 목록), 독자가 모르는 개념을 쓰기 전에 먼저 설명한다. 기술 글에서는 구현 내용만 요약하기보다, 작동 원리를 애니메이션으로 충분히 보여주고 싶어 한다. 초안을 실제 블로그에서 보며 함께 고치는 방식을 선호한다.

2026-10-04에는 k6와 AWS 초안에 'AI스럽다'는 피드백을 받았다. 이때의 편집 방향은 어미만 바꾸기보다 확인된 경험을 앞에 두고, 글의 질문에 직접 필요하지 않은 설정 절차·범위 예고·반복되는 주의사항을 덜어내는 것이다. 정확성을 위한 가정은 계산이나 예제가 등장하는 자리에서 밝히되, 경험의 한계를 본문 곳곳에서 되풀이하지 않는다.

글의 느낌과 구성에 대한 기준으로 kciter.so의 글을 지정했다. 아래 분석은 그 글들을 읽고 도출한 편집 방향이다. 저자의 고유 표현이나 비유를 복제하는 지침은 아니다.

- [서버 모니터링 분석 가이드](https://kciter.so/posts/server-monitoring-analysis-guide/): 독자가 겪을 만한 상황에서 시작하고, 해석에 필요한 관점을 세운 뒤, 그래프의 변화로 원인과 대응을 연결한다. 평균은 같은데 분포가 다른 경우처럼 비교가 설명의 핵심이 된다.
- [브라우저의 메인 스레드는 비싸다](https://kciter.so/posts/the-expensive-main-thread/): 개념을 설명한 다음 독자가 직접 현상을 경험하게 한다. 설정을 바꾸면 무엇이 달라지는지 보여주고, 그 차이를 코드와 연결한다. 해결책이 만드는 비용과 한계도 이어서 다룬다.
- [애니메이션을 설계하는 방법](https://kciter.so/posts/how-to-design-animation/): 움직임을 입력과 상태 변화로 설명한다. 수식, 코드, 조작 가능한 예시가 같은 현상을 서로 다른 방식으로 보여준다.
- [음악 검색 시스템 만들기](https://kciter.so/posts/music-recognition-system/): 전체 시스템을 먼저 보여주고, 필요한 배경 지식을 설명한 뒤, 앞서 설명한 절차를 구현으로 옮긴다. 도식에 있던 단계와 코드의 역할이 연결된다.

참고 글의 기술 주장과 수치까지 검증한 것은 아니다. 글을 새로 쓸 때는 해당 기술의 원문 문서와 실제 코드를 별도로 확인한다.

## 토스 기술 블로그에서 가져온 원칙

사용자가 [토스 기술 블로그](https://toss.tech/)의 설명 방식과 문체를 참고하라고 요청했고, 그중 [토스닥터 글](https://toss.tech/article/toss-doctor)을 문체 기준으로 골랐다. 2026-10-04에 기존 4편을 포함해 20편으로 분석을 넓혔다. 선정한 글과 글별 도입·전개·문체·근거·마무리, 유형별 차이는 [토스 기술 블로그 20편 분석](toss-tech-writing-analysis.md)에 기록했다. 조회수 순위가 아니라 주제와 설명 방식의 다양성을 기준으로 고른 표본이다.

아래는 원문 관찰에서 도출한 이 블로그의 편집 기준이다. 토스의 공식 편집 규칙이나 모든 글이 따르는 공식이 아니다. 기술 주장과 수치는 새 글의 근거로 재사용하지 않고, 표현도 그대로 옮기지 않는다. 토스닥터를 기준으로 한 기존 문체 선호는 유지한다.

### 중심 질문에 맞는 구성을 고른다

초안 전에 독자가 끝까지 읽고 답할 질문을 하나 적는다. 질문에 필요한 설명 순서와 확보한 근거를 기준으로 구성한다. 다음은 선택 가능한 흐름이며 모든 항목을 채우는 목차가 아니다.

| 글의 유형 | 독자가 알고 싶은 것 | 자주 유효한 순서 |
| --- | --- | --- |
| 구현과 문제 해결 | 왜 이 구조가 필요하고 어떻게 움직이는가 | 구체적인 문제 → 요구와 제약 → 해법 → 실행 흐름 → 남은 조건 |
| 개념과 원리 | 어떤 뜻이고 어디까지 성립하는가 | 작은 예시 → 정의와 동작 → 조건 변경 또는 반례 → 적용 범위 |
| 실험과 평가 | 무엇을 비교했고 왜 그 안을 골랐는가 | 질문 → 평가 기준과 조건 → 비교 → 선택 이유 → 손실과 한계 |
| 전환과 마이그레이션 | 기존 동작을 지키면서 어떻게 바꿨는가 | 전환 이유와 대상 → 검증 → 이관 → 복구와 운영 → 결과 |
| 리서치와 발견 | 무엇을 물어 어떤 판단을 바꿨는가 | 결정할 문제 → 조사 방법 → 관찰 → 해석 → 적용 |
| 사례와 문화 | 어떤 시도를 했고 어떻게 이어갈 수 있는가 | 동기 또는 조건 → 사례 → 공통 관찰 → 운영이나 실행 제안 |

구현 경로만 확인됐다면 그 동작과 필요한 조건을 설명한다. 실험이나 개발 경험이 없는 글에 성과, 실패한 시도, 팀의 선택 과정을 만들어 붙이지 않는다. 실제 시간 순서를 재구성하더라도 설명을 위한 순서와 개발 이력을 혼동하지 않는다.

### 도입은 상황과 질문을 준비한다

반복되는 사람의 일, 같은 입력에서 생기는 잘못된 결과, 익숙하지만 설명하기 어려운 현상처럼 독자가 이해할 수 있는 상황에서 시작한다. 낯선 개념을 설명하는 글은 작은 예제나 개념 자체로 시작해도 좋다. 기술 스택과 기능 목록보다 읽어야 하는 이유를 먼저 만든다.

도입에서 중심 질문과 글의 범위를 일찍 알려준다. 결과의 위치는 유형에 맞춰 고른다. 측정 결과가 중심인 글은 결과를 먼저 알려줄 수 있다. 작동 원리가 중심이면 입력과 출력, 무엇을 어디서 실행하는지 짧게 보여준다. 모든 도입에 '하지만 실제로는'이라는 반전이나 '이 글에서는'이라는 안내를 넣지 않는다.

### 절과 문단은 남은 문제로 연결한다

- 절의 역할: 앞에서 드러난 부족함이나 독자의 질문을 다음 절이 해결하게 한다. 구성 요소를 새로 소개할 때는 지금 왜 필요한지 먼저 설명한다.
- 문단의 역할: 하나의 논점 안에서 현상, 이유, 예시, 처리와 범위를 연결한다. 모든 문단을 같은 형식으로 만들거나 교훈 한 줄로 끝내지 않는다.
- 전환의 역할: 무엇이 가능해졌고 무엇이 아직 남았는지 말한다. '이제 다음을 알아보겠습니다'라는 안내만으로 연결을 대신하지 않는다.
- 예시의 역할: 정의나 동작을 바로 확인하게 한다. 개수와 예산은 작은 숫자로, 변환은 전후 코드로, 실행은 입력과 상태로 보여준다. 정의 뒤에 반드시 숫자를 붙이는 규칙은 아니다.
- 명명의 역할: 핵심 개념은 정의한 뒤 같은 이름으로 부른다. 글 자체의 구분이라면 그 범위를 밝히고 일반적인 표준 용어처럼 소개하지 않는다.

짧은 문장은 판단이나 전환을 분명히 할 때 쓰고, 원인을 푸는 문단은 필요한 만큼 이어 쓴다. 한 문장에 한 가지 중심 동작을 두되, 그 동작을 이해하는 데 필요한 조건과 이유까지 무조건 분리하지 않는다. 낯선 전문 용어는 처음 한 번 영어를 병기하고 쉬운 역할 설명을 붙인다.

### 소제목은 해당 절의 일을 드러낸다

사용자가 고른 토스닥터처럼 확인된 동작이나 변화를 문장으로 말하는 제목을 우선 참고한다. 다만 정의와 배경에는 개념형, 구체적인 의문에는 질문형도 쓴다. 결과형 제목은 해당 절에서 그 결과를 뒷받침할 수 있을 때 붙인다.

단계 번호는 실제 순서가 있거나 긴 절의 위치 안내가 필요할 때 사용한다. 병렬인 대안 비교를 순차 절차처럼 만들지 않는다. 질문형 제목을 썼다면 바로 아래 본문에서 답을 시작한다. 목차만 따로 읽어 중심 질문에 답하는 순서가 보이는지 확인한다.

### 코드와 표의 앞뒤에서 근거를 읽어준다

코드 앞에는 확인할 입력과 동작을 알려준다. 코드 뒤에는 그 동작을 만드는 조건이나 변경된 줄을 짚는다. 전후 비교는 중요한 차이에 집중하고, 실패 예시는 실패 조건과 이유까지 설명한다. 함수 이름과 옵션을 나열하는 것으로 작동 원리를 설명했다고 보지 않는다.

표는 같은 기준으로 대안을 비교하고 어떤 차이가 선택을 좌우하는지 설명한다. 그래프는 축, 점이나 막대의 단위, 비교 범위를 알려준다. 그림이나 표 바로 뒤에서는 핵심 변화와 그 의미를 풀되, 매번 같은 안내 문구를 쓰거나 모든 숫자를 본문에 반복하지 않는다.

근거와 주장의 수준을 맞춘다. 코드와 호출 경로는 실행 동작을, 예제 계산은 해당 입력의 결과를, 조건이 기록된 측정은 그 환경의 비교를 뒷받침한다. 사용자의 체감과 통제된 실험을 같은 근거로 쓰지 않는다. 비교 조건, 단위, 기준값을 밝히고 상관관계를 원인으로 단정하지 않는다.

### 선택 이유와 한계는 같은 문제에 연결한다

기술 선택은 확인된 요구, 대안, 판단 기준, 감수한 비용으로 설명한다. 선택한 기술의 장점만 나열하지 않고 다른 안으로도 해결되지 않은 조건을 보여준다. 모든 글에 가상의 대안을 만들거나 선택사를 추가할 필요는 없다.

얻은 것과 치른 비용을 함께 다룬다. 선택을 이해하는 데 필요한 한계는 선택 이유 가까이 두고, 주요한 손실과 후속 문제가 있다면 별도 절로 쓴다. '아직 부족하다' 대신 어떤 입력이나 운영 조건이 해결되지 않는지 구체적으로 적는다. 확인된 장애는 관찰한 신호, 판단, 즉시 대응, 원인과 보완을 연결한다.

### 마무리는 도입의 질문에 답한다

처음의 상황으로 돌아가 무엇이 달라졌는지 정리하거나, 독자가 적용할 조건과 남은 범위를 알려준다. 결론은 본문에서 설명한 장치와 판단으로 뒷받침돼야 한다. 교훈은 근거가 있는 만큼만 쓰며 2~3개를 채우기 위해 만들지 않는다. 모든 글에 '마치며' 절이나 다음 편 예고를 붙일 필요도 없다.

실제로 정해진 다음 작업이 없다면 계획을 지어내지 않는다. 독자에게 제안할 행동은 같은 입력으로 비교해보기, 운영 조건을 점검하기처럼 글의 내용과 연결한다. 보편적인 명언이나 과장된 직무 선언으로 끝내지 않는다.

### 이 블로그에서 줄일 표현

- 인사와 소속 소개는 개인 블로그의 도입에 넣지 않는다.
- 조직 홍보와 참여 제안은 기술 설명의 필수 마무리로 가져오지 않는다.
- 독자 호명, 질문, 감탄은 필요한 자리에만 쓴다. 강연의 말버릇을 문단마다 재현하지 않는다.
- 'A인 것과 B인 것은 다르다' 같은 대조는 한 절에 한 번을 넘기지 않는다. 대조 문장 자체를 여러 절의 핵심 정리로 반복하지 않는다.
- 문체를 참고해도 실제 발언, 당시 감정, 개발 과정, 측정 결과를 만들어 넣지 않는다.

## 어떤 글을 목표로 하는가

독자가 읽기 전에는 설명하지 못했던 현상을, 읽고 나서는 이유와 구현 방법까지 설명할 수 있게 한다. 기술을 얼마나 많이 사용했는지 보여주는 보고서보다, 한 가지 문제를 충분히 이해시키는 기술 글을 목표로 한다.

담백함을 문장 길이와 혼동하지 않는다. 소개 페이지의 문구는 짧아도 되지만, 기술 글은 필요한 설명을 생략하면 오히려 건조한 요약이 된다. 길이가 아니라 각 문장이 하는 일로 판단한다.

### 문장과 문단

- 한 문단에서 하나의 논점을 충분히 설명한다. 매 문장을 한 줄씩 끊거나, 모든 단락을 두 문장으로 제한하지 않는다.
- 앞 문장에서 생긴 의문을 다음 문장에서 풀어준다. 용어 정의를 줄지어 놓는 대신, 지금 그 용어가 왜 필요한지 연결한다.
- 구체적인 입력, 출력, 상태, 결과를 쓴다. '검색 품질을 개선했다'보다 어떤 결과가 잘못 나왔고 어떤 규칙이 순서를 바꾸는지 설명한다.
- 독자에게 말을 걸 수는 있지만, 모든 절을 질문으로 시작하거나 즉답하는 문체로 만들지 않는다.
- 단정할 수 있는 구현은 분명히 쓴다. 조건에 따라 달라지는 동작은 그 조건을 밝힌다. '항상', '완벽하게', '획기적으로' 같은 말은 근거 없이 쓰지 않는다.
- 문체는 토스닥터 글처럼 '~습니다'를 기본으로 하고 '~어요/~죠/~는데요'를 가끔 섞는다(대략 7:3). 사용자가 직접 골랐다. 이 비율은 취향을 기억하기 위한 대략적인 표현이며 토스 20편에서 측정한 통계나 문장별 할당량이 아니다. 구현 사실과 판단 기준은 분명한 정중체로 쓰고, 예시를 꺼내거나 다음 문제를 연결할 때 대화형 어미를 자연스럽게 섞는다. 지나온 시도: 해라체(~다) → 해요체만 쓰기(별로라는 피드백) → 해라체 → 토스닥터식 혼합(확정). '~요'만 이어지면 가볍게 들리고, '~다'만 쓰면 딱딱하게 들린다. 읽는 사람에게 말하므로 1인칭은 '저희'를 쓰되, 확인된 구현만 1인칭으로 말하고 결정 과정이나 시행착오를 지어내지 않는다.
- 제목은 짧고 구체적으로 쓴다. '~보다 나은 ~을 ~으로 만든 방법' 같은 긴 공식형 제목은 AI처럼 들린다는 피드백을 받았다. 사용자가 고른 예: 'GPU 서버도 벡터 DB도 없이 만든 상품 검색'.

### 피할 표현과 고치는 방법

상투어를 금칙어 목록으로만 관리하지 않는다. 문장이 실제 내용을 전달하는지 먼저 본다.

| 약한 문장 | 고치는 방향 |
| --- | --- |
| 다양한 기술을 활용해 효율적인 검색 시스템을 구축했다. | 입력이 무엇이고 후보를 어떻게 찾는지 설명한다. |
| 단순한 유사도를 넘어 사용자의 의도를 이해한다. | 신발끈이 운동화보다 먼저 나오는 사례와 이를 낮추는 규칙을 설명한다. |
| 이 과정에서 중요한 깨달음을 얻었다. | 무엇을 관찰했고 구현을 어떻게 바꿨는지 적는다. 관찰이 확인되지 않으면 경험담으로 쓰지 않는다. |
| 이제 자세히 알아보자. | 다음 절에서 해결할 문제를 구체적으로 연결한다. 전환 문구가 꼭 필요하지 않으면 지운다. |

추상적인 명언, 반복적인 'A가 아니라 B다' 구문, 과장된 성찰로 단락을 끝내지 않는다. 짧은 문장을 나열한 뒤 교훈 한 줄을 붙이는 방식도 반복하지 않는다. 비유는 낯선 개념을 이해시키는 데 필요할 때만 사용하고, 대응하는 기술 요소와 비유가 성립하지 않는 부분을 설명한다.

## 구성은 이해하는 순서로 정한다

아래는 자주 유효한 설명 순서이지 고정 목차가 아니다. 글마다 필요한 부분만 사용한다.

1. 문제 또는 궁금증: 독자가 이해할 수 있는 구체적인 상황을 제시한다.
2. 전체 흐름: 입력이 어디를 거쳐 어떤 결과가 되는지 먼저 보여준다.
3. 필요한 원리: 그 흐름을 이해하는 데 필요한 개념을 등장 순서대로 설명한다.
4. 관찰 또는 비교: 예시나 데모에서 무엇이 바뀌는지 보여준다.
5. 구현: 방금 본 변화가 어떤 코드, 계산, 데이터 구조에서 나오는지 연결한다.
6. 적용 범위: 해결되는 경우, 남는 문제, 추가 확인이 필요한 지점을 적는다.

도입은 스택 목록으로 시작하지 않는다. 특정 프로젝트를 공개하지 않는 글이라면 요구사항을 일반화해서 시작할 수 있다. 가상의 상황은 '가정해보자'처럼 표시하고, 실제로 겪은 일인 것처럼 쓰지 않는다.

소제목은 다음 부분에서 다룰 문제나 개념을 드러내야 한다. 모든 제목을 감성적인 문구나 질문으로 만들지 않는다. 상세한 절이 많다면 목차를 제공하되, 글의 길이를 늘리려고 절을 쪼개지는 않는다.

한 가지 예시를 여러 절에서 이어 사용하는 것이 좋다. 매번 새로운 상품과 상황이 등장하면 독자가 설명보다 예시를 이해하는 데 시간을 쓰게 된다.

마지막은 본문을 그대로 반복하는 요약이나 보편적인 교훈보다, 구현의 적용 범위와 남은 질문으로 마무리한다. 실제로 정해진 다음 작업이 없으면 '앞으로는 ...할 예정이다'라고 지어내지 않는다.

## 애니메이션은 설명의 일부다

각 데모를 만들기 전에 다음 네 가지를 적는다: 독자의 질문, 변하는 조건, 눈여겨볼 변화, 그 변화에서 알 수 있는 사실. 이 중 마지막 항목이 없으면 움직임을 넣을 이유가 약하다.

본문은 데모 앞에서 상황과 관찰 대상을 준비하고, 데모 뒤에서 결과를 해석해 코드와 연결한다. '아래를 보자'만으로 설명을 대신하지 않는다.

### 효과적인 데모

- 같은 입력에 서로 다른 방법을 적용해 비교한다. 벡터 검색만 사용한 결과와 키워드 보정을 더한 결과를 같은 후보로 보여주는 식이다.
- 한 조건이 바뀌면 관련 결과가 함께 바뀌게 한다. 중복 보정이 더해지면 순위와 감점이 함께 변해야 한다.
- 데이터가 어디서 어디로 이동하고 어떤 형태로 바뀌는지 보여준다. 박스의 색만 순서대로 바꾸는 것으로 변환 원리를 설명했다고 보지 않는다.
- 알고리즘을 설명한다면 예시 데이터에서 실제 계산을 수행한다. 미리 정해둔 순서를 재생한다면 절차를 표현한 모식도임을 밝히고, 계산을 재현한 것으로 소개하지 않는다.
- 사진, 벡터, 후보, 결과 사이의 대응 관계를 유지한다. 색과 식별자를 일관되게 사용해 독자가 같은 항목을 따라갈 수 있게 한다.
- 고차원 벡터를 2차원 점으로 그릴 때는 개념도인지 실제 투영인지 명확히 표시한다. 숫자도 임의 값, 측정값, 계산값을 구분한다.

### 그림 디자인

사용자가 시안을 비교해 고른 모양(2026-10-03, '시안 B'): 글 속 코드 블록과 같은 **코드 창 모양**이다. 신호등 점과 제목 막대가 위에 있고, 그 안에 그림, 아래에 번호 알약(①②③)과 색 있는 한 줄 해설이 있다. 바탕은 블로그 종이색에 가까운 `#fffefb`, 글꼴은 블로그 글꼴(시스템 고딕, 눈금·숫자 일부는 Source Code Pro), 주 데이터는 청록빛 파랑 한 가지다. 초록·벽돌·황토·보라는 꾸밈이 아니라 의미(좋음·나쁨·주의·참고)에만 쓴다. 가리키는 부분은 점선과 옅은 음영으로, 여백은 넉넉히 둔다. 같은 상품·구간은 모든 그림에서 같은 색이다. 그림 안 글자와 해설은 '~다/~요'로 끝내지 않고 명사형으로 쓴다('검색 1번에 1장', '스니커즈 B 누락'). 본문 말투가 바뀌어도 그림을 다시 만들 필요가 없다.

처음에는 흰 배경에 파랑·빨강·초록을 쓰는 그림이었는데 종이색 블로그와 어울리지 않는다는 피드백으로 바꿨다. 색 값과 도구는 `docs/figure-runtime.md`에 있다.

움직임으로 보여줄 변화가 없는 개념(구성 비교, 단어 집합, 판단 흐름)은 정지 그림으로 충분하다. 사용자는 이해를 돕는 그림이 많기를 원하므로, 절마다 개념 하나에 그림 하나를 기본으로 생각한다.

### 반복 재생과 읽기

사용자는 버튼을 누르거나 조건을 바꿔야 움직이는 데모보다, 스스로 반복 재생되는 애니메이션을 선호한다. 독자가 조작하지 않아도 한 바퀴 안에서 비교가 끝나야 한다. 본문이 가리키는 상태(후보에서 빠진 상품, 감점 뒤 바뀐 순서 등)에서는 1.5~2.5초 멈춰 읽을 시간을 준다. 한 바퀴 8~13초는 현재 작업 기준이며 사용자가 정한 값은 아니다.

그림은 SVG라서 휴대폰에서도 선명하지만, 폭에 맞춰 줄어들기 때문에 그림 안 글자는 휴대폰 폭에서 절반 이하로 작아진다. 그림에는 식별자, 숫자, 짧은 단계 이름만 넣고 설명은 본문과 해설 줄에 쓴다. 텍스트, 마커, 항목이 겹치지 않도록 장면을 몇 개 뽑아 확인하고 실제 화면에서도 본다. 움직임 줄이기 설정에서는 마지막 장면만 정지해 보여 준다(런타임이 처리한다). 색만으로 상태를 구별하지 않고, `aria-label`에 그림에서 일어나는 변화를 적는다.

데모는 프로젝트의 실서비스를 호출하지 않는 독립적인 예시로 만든다. 글을 읽기 위해 API 키, 로그인, GPU 실행이 필요하면 안 된다. 외부 서비스 호출이나 측정이 필요한 경우에는 사용자가 그 범위를 요청한 뒤 별도로 구현한다.

그림 속 숫자는 손으로 적지 않고 예시 데이터에서 계산한다. 계산은 `scripts/figure_data/*.py`에서 하고, 본문 숫자와 맞는지 `assert`로 확인한 뒤 `assets/figures/*-data.js`로 내보낸다. 브라우저는 그 값을 그리기만 한다. 그림 정의와 만드는 방법은 `docs/figure-runtime.md`를 따른다. 글에 스크립트를 넣는 경우에는 `soft-nav.js`가 글 안의 script를 다시 실행하므로 전역 선언 충돌, 중복 초기화, 떠난 페이지의 타이머를 확인한다(그림 런타임은 이미 처리해 두었다). 데스크톱과 모바일에서 렌더링을 직접 검사한다. 검사가 안 된 부분은 완료했다고 보고하지 않는다.

## 코드, 근거, 익명화

사용한 기술, 실행 경로, 남아 있는 보조 코드, 실제 동작을 구분한다. 저장소에 번역 함수가 있다는 이유만으로 모든 검색어가 번역된다고 쓰지 않는다. 주석보다 현재 호출 경로를 확인한다.

코드는 독자가 방금 이해한 원리를 구현하는 데 필요한 부분만 제시한다. 원본 코드, 설명을 위해 줄인 코드, 의사 코드를 구분하고, 생략한 부분 때문에 실행할 수 없다면 알린다. 모델 버전이나 API 동작을 설명할 때는 공식 문서로 확인한다.

성능과 비용의 개선을 주장하려면 측정 조건과 근거가 필요하다. 근거가 없으면 구조를 설명하고 비교 결과는 쓰지 않는다. 다만 비용은 사용자가 계산해서 보여주길 원한다. 측정값이 없을 때는 공식 요금표의 단가에 명시한 가정(상품 수, 검색 수, 토큰 수 등)을 곱해 계산하고, 단가 출처와 확인 날짜, 가정 표, 계산식, 계산에서 빠진 항목(무료 사용량, 측정하지 않은 서버 비용 등)을 함께 적는다. 이 값을 실제 청구액이나 측정값으로 소개하지 않는다. 계산은 그림 생성 스크립트 안에서 하고 본문 숫자와 맞는지 assert로 확인한다. 재시도나 폴백 경로도 구현된 범위만 설명한다.

프로젝트 익명화를 요청받으면 다음 항목을 본문, 코드, 파일명, 그림, 캡션, 링크에서 확인한다.

- 프로젝트명, 고객사명, 저장소 주소, 내부 서비스명과 도메인.
- 실제 상품번호, 업무 데이터, 식별 가능한 이미지와 화면.
- 환경 변수 값, 인증 정보, 로그에 포함된 민감한 내용.

프로젝트의 사실은 코드로 확인할 수 있지만, 그 기술을 선택한 당시의 이유와 시행착오는 사용자 확인이 필요하다. 미확인 경험을 1인칭으로 만들지 않는다. 공개 글 밖의 편집 메모에 질문을 남긴다.

## 초안부터 수정까지

1. 구현에서 확인한 사실과 사용자에게 확인할 경험을 나눠 적는다.
2. 글에서 답할 중심 질문을 하나 정하고, 필요한 개념과 데모를 배치한다.
3. 본문과 데모를 함께 작성해 로컬에서 읽을 수 있게 한다. 글 전체를 애니메이션 제작 계획으로 대체하지 않는다.
4. 사용자에게 초안 위치와 미확인 내용을 짧게 전달한다. 여러 취향 질문을 한꺼번에 요구하지 않는다.
5. 피드백을 반영하면서 반복적으로 확인된 취향을 이 가이드에 추가한다. 일회성 요청을 모든 글의 규칙으로 확대하지 않는다.

초안 검토에서는 중심 질문에 답하는지, 소제목만으로 흐름이 보이는지, 낯선 개념의 예시가 준비됐는지, 코드와 그림 뒤에 해석이 있는지 확인한다. 선택의 이유와 결과가 확보한 근거를 넘지 않는지, 한계가 구체적인지, 마무리가 본문으로 뒷받침되는지도 읽는다. 이 검토를 고정 목차나 별도의 발행 승인 절차로 만들지 않는다.

기존 글의 발행 요청을 새 초안의 발행 허가로 해석하지 않는다. 로컬 미리보기와 원격 발행을 구분한다. 내부 편집 지침은 `_config.yml`의 `exclude`에 넣어 사이트에 노출하지 않는다. Git 저장소 자체의 접근 권한은 별개의 문제다.

## 현재 검색 글에 적용할 방향

초안은 구현 요약에서 출발했다. 현재 그림은 예시 데이터(`scripts/figure_data/`)로 계산해 브라우저가 그리는 반복 애니메이션과 정지 그림이다. 참고 글의 설명 방식에 맞춰 고칠 때는 다음을 우선한다.

- 도입에서 사진 검색과 이름 검색이 각각 해결하는 문제를 분명히 한다.
- 임베딩을 단순히 '숫자 배열'이라고 정의하고 넘어가지 않는다. 같은 모델로 비교해야 하는 이유와 코사인 거리의 의미를 예시로 풀어준다.
- 후보 수집과 순위 결정이 다른 문제임을 보여준다. 후보에 들어오지 못한 항목은 뒤의 보정으로 복구할 수 없다는 한계를 연결한다.
- 순위 보정과 중복 보정은 같은 후보가 단계별로 다시 정렬되는 반복 애니메이션으로 비교한다. 예시에서 실제로 계산한 결과와 설명용 모식도를 구분한다.
- 사용자 확인(2026-10-02): 텍스트 임베딩은 Voyage의 voyage-multilingual-2, 대량 등록 GPU는 Modal의 T4다.
- 모델 선택과 CPU/GPU 역할 분담은 확인된 구현만 설명한다. 당시 선택 이유나 성능 개선 이야기는 사용자에게 확인한 뒤 쓴다.
- 사용자가 밝힌 주제는 '최소 비용으로 키워드 검색보다 나은 검색 엔진을 직접 만든다'는 것이다. 사용자의 문구를 그대로 옮기지 않고, 무엇을 더 잘하게 됐는지(사진 검색, 뜻으로 찾기, 순서 보정)와 무엇을 따로 두지 않았는지로 보여준다. 측정값이 없으므로 비용 절감 폭은 쓰지 않는다.

이 적용안은 아직 사용자와 함께 다듬는 중이며, 완성된 글의 필수 목차가 아니다.
